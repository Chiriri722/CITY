# 기존 환경 재사용 및 중복 설치 정리 계획

조사일: 2026-10-10. 기준: CITY `18bd1ec` (v.0.1.11).
상태: 아래 계획에 따른 실행 코드와 README 반영. 사용자 기기의 실행·로그인 유지 검증과 구 환경 정리는 사용자 확인 단계로 남김.

## 구현 반영 요약

- `status`: 체크아웃 커밋/경로, distro/rootfs, 관리 상태와 기록된 에이전트 버전 조회. 패키지/PRoot/에이전트를 실행하거나 표식을 변경하지 않는다.
- `update [agent|all]`: 기존 관리 환경의 설치된 에이전트만 갱신한다. 환경 생성은 `install`만 담당한다.
- 기존 설치 흐름·잠금·체크섬·기동 확인·활성 링크 전환을 재사용한다.
- `scripts/environment.sh`: 읽기 전용 환경/에이전트 검사와 관리 표식 이전을 모아 설치/업데이트/상태 조회가 같은 판정을 사용한다.
- 관리 표식은 `CITY_ENV_V1`, OS ID, 릴리스, 아키텍처, 생성 당시 이미지의 다섯 줄이다. 레거시 이미지는 알려진 출처만 허용하고 실제 OS와 Bash ELF 아키텍처를 대조한다. 새로운 기본 이미지와 출처 기록은 분리한다.
- README에 첫 설치와 업데이트를 구분하고 CITY3 유지 예제, 상태 설명, 별칭 및 별도 홈 백업 안내를 추가했다.
- 자동 삭제나 임의 컨테이너 인수 기능은 추가하지 않았다. 별도 `ubuntu`는 계속 독립 환경으로 남긴다.
- 검증: 기본 검사 20개와 ShellCheck·Bash 구문 통과. Ubuntu 24.04/ Debian 12 x64의 실제 rootfs와 Termux PRoot에서 설치·두 차례 업데이트·다섯 CLI 실행·Python/venv·무결성 실패 시 링크 보존을 확인했고, distro 생성은 각각 한 번이었다. Android 기기 검증은 별도로 남아 있다.

아래는 조사 당시의 설계 근거다. 최신 사용자 실행 절차와 검증 결과는 [README](../README.md)를 따른다.

## 확인한 구조

| 대상 | 역할 | 현재 동작 |
| --- | --- | --- |
| `$HOME/CITY`, `CITY2`, `CITY3` | 설치기·런처를 담은 Git 체크아웃 | 폴더명으로 배포판 이름을 만들지 않음 |
| `city-ubuntu`, `city-debian` | 실제 PRoot 컨테이너 | `CITY_DISTRO`로 선택. 기본 Ubuntu |
| 게스트 `/opt/city` | Node와 CLI 설치 위치 | 버전별 디렉터리 및 활성 심볼릭 링크 |
| Termux `$HOME` | 프로젝트와 사용자 설정 | 에이전트 실행 때 게스트 `/root`에 공유 |

`city.sh:85`가 컨테이너 이름을 정하고, 111–125행이 기존 컨테이너를 확인한다. 컨테이너가 없을 때만 rootfs를 생성한다. `343b06d`, `e3907f2`에서도 이름 결정 방식은 동일하다. 따라서 같은 Termux 앱/저장소에서 같은 `CITY_DISTRO`를 사용했다면 체크아웃이 세 개여도 실제 배포판은 공유한다.

현재 설치기를 같은 배포판에 다시 실행하면 기존 rootfs에 필요한 패키지와 에이전트를 설치한다. 정상으로 확인된 동일 버전은 재사용하고 새 버전은 검증 후 링크를 교체한다. 지원 대상 추가 자체는 새로운 distro를 요구하지 않는다.

사용자가 2026-10-10 전달한 `proot-distro list` 결과는 **`city-ubuntu`, `ubuntu` 두 개**다. 따라서 해당 Termux 저장소에서 CITY/CITY2/CITY3가 세 개의 독립 distro를 뜻하지는 않는다. 현재 코드의 기본 대상은 `city-ubuntu`이며, 별도의 `ubuntu`는 자동 선택하거나 수정하지 않는다. `ubuntu`의 설치 출처·사용 도구·보관 데이터와 단말의 실제 별칭 대상은 아직 미확인이다.

이 기기에서는 우선 `city-ubuntu`를 유지 대상으로 삼고, CITY 체크아웃 하나를 계속 갱신하는 경로가 적합하다. `ubuntu`는 단지 이름이 다르다는 이유로 폐기하지 않는다. 기존 앱이나 에이전트가 사용 중이면 독립적으로 유지한다. 불필요한 환경임이 확인되는 경우에만 백업·선별 이전·검증 후 정리한다.

## 지금 가능한 운영 방식

1. 현재 정상 동작하는 체크아웃 하나를 계속 사용한다. 이름이 `CITY3`여도 무방하며, 이름을 맞추기 위한 이동은 필요 없다.
2. 새 릴리스마다 새로 clone하지 않고 같은 체크아웃을 갱신한다. 로컬 수정이 있으면 먼저 차이를 확인하며 강제 reset하지 않는다.
3. 기존과 같은 `CITY_DISTRO`를 명시하고 필요한 에이전트의 `install`을 다시 실행한다.
4. 셸 별칭은 선택한 체크아웃 하나를 가리키게 한다. 오래된 설치기를 다시 실행하면 공유 환경의 에이전트 활성 링크가 과거 버전으로 돌아갈 수 있다.

예: 기존 환경이 Ubuntu이고 앞으로 CITY3 체크아웃을 유지할 경우. 아래는 적용 단계의 예시이며 이번 조사에서는 실행하지 않았다.

```bash
git -C "$HOME/CITY3" status --short
# 로컬 변경을 확인한 뒤, 해당 체크아웃을 정상적으로 갱신할 수 있을 때:
git -C "$HOME/CITY3" pull --ff-only
CITY_DISTRO=ubuntu bash "$HOME/CITY3/city.sh" install muse
CITY_DISTRO=ubuntu bash "$HOME/CITY3/city.sh" muse
```

`install all`은 지원되는 모든 CLI를 추가하는 의미다. 이미 설치한 CLI만 갱신하는 명령은 아직 없다. 시스템 패키지 설치도 함께 수행하므로 전체 변경이 하나의 트랜잭션인 것은 아니다.

## 구현 계획

### 1. 상태 표시와 문서부터 보강

- `status` 명령: 체크아웃 경로/버전, 대상 distro, rootfs 경로, 관리 표식 상태, 설치된 에이전트와 활성 버전 표시.
- 조회 중에는 패키지 설치·컨테이너 생성·로그인 설정 변경을 하지 않는다. 인증 파일 내용은 출력하지 않는다.
- 설치 시작과 완료 메시지에서 기존 환경 재사용/새 환경 생성 여부를 구분한다.
- README에서 첫 설치와 기존 사용자 갱신 절차를 분리한다. 복제 폴더 수가 환경 수가 아니라는 점을 설명한다.

### 2. 기존 환경 전용 업데이트 추가

- 제안 명령: `bash city.sh update [agent|all]`. **아직 구현된 명령이 아니다.**
- 대상 컨테이너가 없으면 중단하며 새 distro를 생성하지 않는다.
- 인자 생략 또는 `all`은 관리 표식과 활성 링크로 확인된 설치 에이전트만 갱신한다. 미설치 에이전트를 지정하면 `install`을 안내한다.
- 업데이트 기준은 현재 CITY 체크아웃에 기록된 공식 URL·버전·체크섬이다. 공급자의 최신 릴리스를 무조건 내려받지 않는다.
- Git 체크아웃 갱신과 게스트 패키지 갱신은 구분한다. `update`가 사용자 Git 수정사항을 덮어쓰지 않는다.
- 기존 설치 잠금과 임시 설치·체크섬·기동 확인·링크 교체 절차를 재사용한다. 공유 설치/실행 대상 결정 로직이 서로 달라지지 않도록 한다.
- 기본 distro 이름은 유지한다. 사용자 기기에 별도 이름의 실제 컨테이너가 확인될 때만 명시적인 기존 대상 선택 기능을 추가 검토한다. 이름만 보고 자동 편입하지 않는다.

### 3. 이미지 출처와 환경 식별 분리

현재 `.city-owner`에는 생성 당시 이미지 digest가 기록되며, 설치 시 이것이 **현재 코드의** 이미지 digest와 같아야 한다. 향후 기본 이미지만 갱신해도 정상적인 기존 환경이 `Refusing unmanaged distro`로 거부될 수 있다.

- 생성 당시 이미지 digest는 출처 기록으로 보존하고, CITY 관리 여부와 기반 OS 호환성 판정에서 분리한다.
- 기존 표식은 알려진 과거 CITY digest인지 확인하고 OS ID/릴리스·아키텍처와 대조한 뒤 명시된 호환 범위에서만 이전한다.
- 모르는 표식, 누락된 표식, 심볼릭 링크로 바뀐 rootfs 등 기존 거부 조건을 무조건 통과시키지 않는다. OS가 맞는다는 이유만으로 임의 컨테이너를 인수하지 않는다.
- CLI 추가/갱신은 같은 OS에서 수행한다. Ubuntu ↔ Debian 전환이나 OS 메이저 업그레이드는 별도 이전 작업으로 분리한다.
- 새 이미지 digest를 기존 환경의 출처인 것처럼 덮어쓰거나, 이를 맞추려고 distro를 재설치하지 않는다.

## 구 환경 정리 순서

1. **분류:** distro는 사용자 확인 결과 `city-ubuntu`, `ubuntu` 두 개다. 각 체크아웃 버전/로컬 수정, 별칭 대상, `ubuntu` 사용 도구, 프로젝트·가상환경 위치를 추가 확인해 정리 대상 경로를 확정한다.
2. **보존:** 작업 중인 에이전트를 종료한 뒤 컨테이너 백업과 Termux 홈의 프로젝트·숨김 설정 백업을 별도로 준비한다. 백업 출력이 다시 백업에 포함되지 않도록 위치를 분리한다.
3. **선택:** 정상 환경 하나를 유지한다. 실제 distro가 하나라면 환경 이전은 필요 없고 체크아웃·별칭만 정리한다.
4. **중복 distro가 있을 때:** 유지할 환경에 필요한 CLI를 설치하고, 다른 환경에만 있는 작업물·설정·추가 패키지 내역을 확인해 선별 이전한다. 서로 다른 OS의 `/usr`나 rootfs 전체를 합치지 않는다. 경로나 Python/OS가 달라진 venv는 의존성 기록을 이용해 재생성한다.
5. **확인:** CLI 버전, 기존 로그인/설정, 프로젝트 접근, Python/cryptography, 대표 작업 실행과 종료를 확인한다. 컨테이너 백업 복원 시험은 운영 환경을 덮어쓰지 않는 별도 시험 환경에서 수행한다.
6. **정리:** 위 확인 후 불필요한 체크아웃을 정리한다. 체크아웃 안에 프로젝트나 `.venv`가 있을 수 있으므로 폴더 이름만 보고 지우지 않는다. 별도 distro 삭제는 정확한 이름과 백업을 확인한 뒤 별도 단계로 수행한다.

초기 구현에 자동 삭제 기능은 넣지 않는다. `/opt/city`의 구버전 디렉터리는 실제로 별도 공간을 차지하지만 distro 전체 복제와는 다르다. 활성 버전과 복구용 이전 버전을 보존한 뒤 나머지 정리 여부를 판단한다.

## 검증 기준

- 체크아웃 경로가 CITY/CITY2/CITY3로 달라도 같은 설정이면 같은 컨테이너를 선택한다.
- 지원 대상 추가 및 반복 업데이트 후에도 컨테이너 수와 기존 프로젝트·설정이 유지된다.
- 미설치 환경에서 `update`는 생성 없이 실패하고, `install`만 최초 생성을 담당한다.
- 새 CLI 설치와 기존 CLI 업데이트 대상이 구분되며, 잘못된 URL/체크섬과 기동 실패 시 기존 활성 링크가 유지된다.
- 기존 관리 표식 이전, 허용된 과거 이미지 재사용, 알 수 없는 환경 거부를 각각 검사한다.
- 기존 네트워크 없는 검사 및 Ubuntu/Debian 설치 통합 검사를 확장한다. 실제 기기의 백업·복구와 로그인 유지도 별도 확인한다.

## 공식 문서 확인

[PRoot-Distro v5.8.0 문서](https://github.com/termux/proot-distro/blob/v5.8.0/README.md)를 기준으로 조사했다. 적용 시에는 단말에 설치된 버전의 `--help`와 저장 구조를 대조한다.

- `--shared-home`은 호스트 홈을 게스트 `/root`에 연결한다. `backup`의 대상은 컨테이너 manifest와 rootfs이므로 공유 홈까지 보존됐다고 가정하면 안 된다.
- `backup`/`restore`가 제공된다. `restore`는 같은 이름의 기존 rootfs를 비우므로 단순 검사용으로 운영 컨테이너에 실행하지 않는다.
- `remove`는 컨테이너를 영구 삭제하며 `reset`도 기존 데이터를 없앤다. 둘 다 일반 업데이트 절차로 사용하지 않는다.
- 컨테이너 이름 변경이 필요하면 내부 링크를 보정하는 공식 `rename`을 사용한다. rootfs 디렉터리를 임의로 옮기는 방식은 피한다.
